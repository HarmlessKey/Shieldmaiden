Generated from `npm run verify:5.5e-content -- --type=monster` against
[emulator/database.rules.json](../emulator/database.rules.json) (the real prod
RTDB rules dropped in per `.planning/5.5e-content-firebase-verification.md`
§0), after the `size`/`type` casing fix and the `_id`/`__v`/`url`/
`initiative_modifier` rules additions were applied (the latter three have
since regressed — see [Regression](#regression-_id__vurl-dropped-from-the-rules)).

**Result: 195/330 passed, 135 failed.**

Every failure was bisected against the live emulator (single-field removal
from the real, failing payload — the field(s) whose removal alone flips the
write from `permission_denied` to success). Full per-monster raw output:
`scripts/verify-5.5e-content/results/2026-08-11T11-04-19-742Z.json` (report)
and the bisection dump (not committed — regenerate via the bisection approach
below if needed).

**Update:** causes 1, 2, and 5 have since been fixed in the rules and
re-verified individually (see each section below). A regression was found
in the same pass — see [Regression](#regression-_id__vurl-dropped-from-the-rules)
— that's currently masking whether 1/2/5 hold up on full real payloads, not
just in isolation.

## Root causes (5 total)

All 135 failures reduce to five distinct causes. Three (1, 2, 5) were "the npc
RTDB rules don't know about this field/shape at all" (blocked by
`"$other": { ".validate": false }"` or a too-strict enum) and have been fixed
in the rules. The other two (3, 4) turned out to be data problems, not rules
problems — the data itself is being corrected instead.

### 1. `bonus_actions` — new top-level field, not in the rules (72 monsters) — ✅ RESOLVED

5.5e split some monster actions into a distinct "Bonus Actions" block (5e kept
everything under `actions`). Shape mirrors the existing `actions` field
exactly (`name`, `desc`, `action_list`, etc.), e.g. `elephant`'s "Trample".
There is no `bonus_actions` key anywhere in the `npcs/$uid/$npcId` rules.

**Fix:** add a `bonus_actions` block to the rules, structurally identical to
the existing `actions` block ([emulator/database.rules.json:1089](../emulator/database.rules.json#L1089)).

**Verified:** added, mirrors the `actions` shape. Isolated test (`required
fields + bonus_actions` only) passes for `elephant`. Full real payloads for
`bonus_actions` monsters still fail, but only because of the `_id`/`__v`
regression below — not this field.

### 2. `gear` — new top-level field, not in the rules (45 monsters) — ✅ RESOLVED

A plain string field on humanoid stat blocks listing equipment, e.g.
`bandit.gear = "Leather Armor, Light Crossbow, Scimitar"`. Not in the rules
at all.

**Fix:** add a simple string `.validate` (matching the pattern used for
`hit_dice`/`harmless_key`, e.g. `newData.isString() && newData.val().length <= 500`).

**Verified:** added at [emulator/database.rules.json:580](../emulator/database.rules.json#L580)
as `newData.isString() && newData.val().length <= 2000`. Isolated test
(`required fields + gear` only) passes for `bandit`. Full real payloads for
`gear` monsters still fail, but only because of the `_id`/`__v` regression
below — not this field.

### 3. `innate_level` — new field, not in the rules (50 monsters) — ⏳ FIX IN PROGRESS (data-side)

Sits alongside the existing `innate_ability`/`innate_save_dc`/
`innate_spell_attack`/`innate_spells` cluster ([emulator/database.rules.json:783](../emulator/database.rules.json#L783))
but isn't itself defined, e.g. `adult-black-dragon.innate_level = 4`.

**Decision:** `innate_level` wasn't supposed to be on these monsters in the
first place — it's being removed from the monster data rather than added to
the rules. No rules change needed; this resolves once the data update lands.

### 4. `legendary_actions` — required field no longer in the data (30 monsters) — ⏳ FIX IN PROGRESS (data-side)

Different from the other three: `legendary_actions` **is** in the rules, but
its `.validate` requires `hasChildren(['name', 'legendary_cost'])`
([emulator/database.rules.json:1088](../emulator/database.rules.json#L1088)).
5.5e legendary action entries (e.g. `aboleth`) only have `name`, `desc`, and
`action_list` — no `legendary_cost` at all.

**Decision:** `legendary_cost` will always be populated on legendary actions
going forward — the data was missing it, not the rules being wrong. No rules
change needed; this resolves once the data update lands.

### 5. `swarm-of-crawling-claws` — `type` enum too narrow (1 monster, special case) — ✅ RESOLVED

Not part of the four counts above. Its `type` is `"Swarm of tiny undead"`,
but the rules' `type` enum only allowed the literal string
`"Swarm of tiny beasts"` ([emulator/database.rules.json:529](../emulator/database.rules.json#L529)) —
no other swarm-of-tiny-X creature type was accepted. Confirmed directly:
`type: "Swarm of tiny beasts"` writes fine, `type: "Swarm of tiny undead"`
doesn't. There are presumably more "Swarm of tiny X" types in the full 5.5e
set beyond this one sample.

**Fix:** broadened the regex to `Swarm of tiny (beasts|undead)` — only
covers the two variants seen so far; the full list of swarm sub-types the
API can return is still unconfirmed.

**Verified:** isolated test (`required fields` only, with `type: "Swarm of
tiny undead"`) now passes for `swarm-of-crawling-claws`. Its full real
payload still fails, but only because of the `_id`/`__v` regression below —
not this field.

## Regression: `_id`/`__v`/`url` dropped from the rules

Before this batch of fixes (1/2/5 above), the very first monster checked
(`axe-beak`) failed on `_id`, `__v`, and `url` — MongoDB/API artifacts not in
the rules' schema (see the original diagnosis earlier in this task). Those
three were added to the rules and verified working at the time.

They are **no longer in the rules file** — only `source` remains at
[emulator/database.rules.json:513](../emulator/database.rules.json#L513);
`url`/`_id`/`__v` are gone. Unclear exactly when — likely dropped
incidentally while editing in `gear`/`bonus_actions`/the `type` enum fix.

**Effect:** every monster payload includes `_id` and `__v` (all API
responses do), so **every monster still fails end-to-end** even though
causes 1, 2, and 5 are individually fixed — confirmed directly: `elephant`,
`bandit`, and `swarm-of-crawling-claws` still get `permission_denied` on
their full payload, but each passes once `_id`/`__v` are excluded from the
test write.

**Fix:** re-add the three entries removed, e.g. next to `source`:
```json
"url": { ".validate": "newData.isString() && newData.val().length <= 100" },
"_id": { ".validate": "newData.isString() && newData.val().matches(/^[0-9a-f]{24}$/)" },
"__v": { ".validate": "newData.isNumber()" }
```
