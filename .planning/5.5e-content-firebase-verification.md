# 5.5e SRD content vs. Firebase rules verification — plan

**Status: PLAN — not yet implemented.**

Goal: on `feature/5.5e-spell-firebase-verification`, build a local-only test
harness that pulls every 5.5e SRD monster and spell from the compendium API,
runs it through the app's real save path, and writes it to the Firebase
emulator — loaded with the **real** RTDB/Storage rules — so we get a pass/fail
report of which 5.5e content the actual security rules would reject.

---

## 0. Blocking dependency — the emulator has no real rules yet

`emulator/database.rules.json` and `emulator/storage.rules` (added in the
Firebase-emulator branch just merged into this branch) are intentionally
**wide open** (`{ ".read": true, ".write": true }`) — that was iteration 1 of
a separate effort (offline dev), and by design nothing in this repo ever
touches the production ruleset (see `.planning/firebase-emulator-local-dev.md`
§6a guardrail: no `.firebaserc`, config file deliberately not named
`firebase.json`).

This task needs the opposite: the emulator must be loaded with the **actual**

## 1. How content actually gets saved today (the path we must replicate)

Traced from the app code, not assumed:

**Monsters:**
1. `monsterServices.getMonster(slug, "5.5e")` → `GET {VUE_APP_HK_API_ROOT}/monsters/5.5e/{slug}` (`src/services/api/monsters.js:83`)
2. `api_monsters/fetch_monster` action wraps it, adds `meta` tags, caches (`src/store/modules/content/monsters.js`)
3. UI copy flow (`CopyContent.vue` → `EditNpc.vue`) takes the raw monster object and runs `convertVersatileToOptions()` on it (`EditNpc.vue:320`) — reshapes `versatile` weapon actions into an `options` structure. This is the only structural transform before save.
4. Save calls Vuex `npcs/add_npc` (`src/store/modules/userContent/npcs.js:178`), which:
   - requires `rootGetters.user.uid` (must be signed in)
   - checks `getNpcCount(uid) >= rootGetters.tier.benefits.npcs` and **silently returns the string `"Not enough slots"` instead of writing** if over quota — app-level business logic, unrelated to Firebase rules
   - builds `search_npc` via `convert_npc()` (whitelist: `name, challenge_rating, avatar, storage_avatar, type, groups`)
   - calls `npcServices.addNpc(uid, npc, search_npc)` (`src/services/npcs.js:65`), which is the actual Firebase write:
     - `npcs/{uid}/{pushId}` ← full npc object (+ `created`/`updated` server timestamps, lowercased `name`)
     - `search_npcs/{uid}/results/{pushId}` ← compressed `search_npc`

**Spells:**
1. `spellServices.getSpell(slug, "5.5e")` → `GET {VUE_APP_HK_API_ROOT}/spells/5.5e/{slug}` (`src/services/api/spells.js:66`)
2. `api_spells/fetch_api_spell` wraps/caches it (`src/store/modules/content/spells.js`)
3. `EditSpell.vue` assigns the fetched object directly to the form model — no structural transform.
4. Save calls Vuex `spells/add_spell` (`src/store/modules/userContent/spells.js:132`) → `convert_spell()` (whitelist: `name, school, level`) → `SpellServices.addSpell(uid, spell, search_spell)` (`src/services/spells.js`):
   - `spells/{uid}/{pushId}` ← full spell object
   - `search_spells/{uid}/results/{pushId}` ← compressed `search_spell`

**Critical point for rules-testing:** `add_npc`/`add_spell` (the Vuex actions)
gate on tier/slot quotas that have nothing to do with Firebase rules, and
require a fully bootstrapped store (`rootGetters.tier`, etc.). The actual
rules-enforcement boundary is the **service layer** (`npcServices.addNpc`,
`SpellServices.addSpell`) — those call `db.ref(...).set()`/`.push()` directly.
**Plan: call the service classes directly**, not the Vuex actions, so the
harness tests exactly what the rules allow/reject without app quota logic
getting in the way. (Open question for you in §6 if you'd rather go through
the Vuex actions and seed a generous tier instead.)

## 2. Second critical point: client SDK, not admin SDK

`firebase-admin` (used in `src-ssr/api/index.js`) **always bypasses RTDB
security rules**, emulator or not — that's true of the real Admin SDK and
still true when it's pointed at the emulator via
`FIREBASE_DATABASE_EMULATOR_HOST`. If the harness writes with `admin.*`, every
write "succeeds" regardless of what the rules say, and the whole exercise
becomes a no-op.

The harness must therefore:
1. Use the **Auth emulator** to create/sign in a real user (via the client SDK
   or the Auth emulator's REST API), getting a normal (unsigned-but-shaped)
   ID token.
2. Use the **client SDK** (`firebase` v8, same package the app uses),
   `useEmulator()`-wired exactly like `src/firebase.js` already does, signed
   in as that user, to perform the `npcs/{uid}/...` and `spells/{uid}/...`
   writes.
3. Admin SDK is only used for setup convenience (e.g. `admin.auth().createUser`
   to provision the test account without going through the sign-up UI flow) —
   never for the writes being measured.

## 3. Enumerating "every 5.5e SRD monster/spell"

`monsterServices.getMonsters` / `spellServices.getSpells` already support
`query.source` and pagination (`src/services/api/{monsters,spells}.js`). Need
to confirm against the live API (not visible from this sandbox) what source
value isolates 5.5e SRD content — likely `source=srd` or similar — and that
`fields=["url"]` (or `id`) is enough to get a lightweight slug list. First
implementation step is a throwaway discovery call:

```
GET {VUE_APP_HK_API_ROOT}/monsters/5.5e?limit=1&fields=source
GET {VUE_APP_HK_API_ROOT}/spells/5.5e?limit=1&fields=source
```
to see the actual `source` field values, then page through with
`skip`/`limit` (`pageSize`) collecting every `url`/slug where source matches
SRD, for both monsters and spells.

## 4. Harness design

New standalone Node script(s), not a Jest/Mocha suite (repo has no test
runner configured — `npm test` is a no-op placeholder). Plain Node matches
how `npm run emulators` / `npm run ssr:emulator` already work as manual local
tooling.

```
scripts/verify-5.5e-content/
  index.js            # entrypoint, orchestrates the run
  discover-slugs.js    # §3 — list all 5.5e SRD monster/spell slugs from the HK API
  fetch-content.js      # GET /monsters/5.5e/{slug} and /spells/5.5e/{slug}
  save-monster.js        # replicate EditNpc.vue's convertVersatileToOptions + npcServices.addNpc, signed in as test user
  save-spell.js            # replicate SpellServices.addSpell, signed in as test user
  report.js                 # collect results, print summary + write JSON report
```

```jsonc
// package.json addition
"scripts": {
  "verify:5.5e-content": "node scripts/verify-5.5e-content/index.js"
}
```

### Flow

1. **Preflight**: confirm `firebase.emulator.json` emulators are reachable
   (Auth :9099, DB :9000) — fail fast with a clear message if
   `npm run emulators` isn't already running in another terminal.
2. **Provision test user**: `admin.auth().createUser({ uid: "verify-5.5e-content" })`
   against the Auth emulator (admin SDK is fine here — user provisioning
   doesn't touch RTDB rules), then sign in that same user via the **client**
   SDK using a custom token (`admin.auth().createCustomToken(uid)` →
   `firebase.auth().signInWithCustomToken()`), so `auth.currentUser` /
   `auth.uid` is populated exactly like a real session for the RTDB rules to
   evaluate against.
3. **Discover slugs** (§3) for `monsters/5.5e` and `spells/5.5e`, SRD source
   only.
4. **For each monster slug**:
   - fetch full monster via `GET /monsters/5.5e/{slug}`
   - run `convertVersatileToOptions()` (ported verbatim from `EditNpc.vue`)
   - call `npcServices.addNpc(testUid, npc, convert_npc(npc), slug)` — pass
     the slug as `predefined_key` so reruns overwrite the same path instead of
     accumulating junk in the emulator
   - record `{ slug, name, status: "pass" | "fail", error }` — Firebase
     `PERMISSION_DENIED` (or any thrown error) is a `fail`, not a script crash
5. **For each spell slug**: same shape, using `SpellServices.addSpell` +
   `convert_spell()`, no structural transform needed (per §1).
6. **Report**: console summary table (pass/fail counts, first N failures with
   the actual Firebase error message) + write full results to
   `scripts/verify-5.5e-content/results/<timestamp>.json` (gitignored) for
   diffing between reruns as rules or SRD content change.

### Auth/env wiring

Reuses the existing emulator plumbing from `.planning/firebase-emulator-local-dev.md`
verbatim — same `.env.emulator` values, same `src/firebase.js` `useEmulator()`
block. The script sets `USE_FIREBASE_EMULATOR=true` and imports `src/firebase.js`
(or duplicates the tiny init, since this is a plain Node script outside the
Quasar/webpack build — needs deciding, see §6) rather than re-deriving the
emulator hosts/ports.

## 5. Reading the results

Once real rules are loaded (§0), a `fail` on a given slug means: the shape the
app actually produces for that SRD monster/spell — as the *5.5e* edition
specifically — doesn't satisfy the current production rules. That's the
signal this task exists to surface, e.g.:
- a 5.5e-only field the rules don't know about (validated against an
  allowlist of keys and rejected)
- a type mismatch (e.g. a field that's a string in 5e data and a number/object
  in 5.5e data)
- a size/depth limit tripped by 5.5e's more verbose ability descriptions

Each failure should be actionable: which slug, which top-level field the
rules rejected (RTDB errors usually name the path), and the actual vs.
expected shape.

2. **Vuex actions vs. service layer** (§1) — okay to call `npcServices`/

3. **SRD `source` filter value** (§3) — I can't reach `api.harmlesskey.com`
   from this sandbox to inspect it directly; fine for me to hardcode a
   best-guess (`source=srd`) and adjust once the script is run against the
   real API, or do you already know the exact value?
4. **Script runtime** (§4 "Auth/env wiring") — plain Node script that
   duplicates the small `firebase.js` emulator-init snippet, vs. running it
   through `quasar dev`'s Node context so it can `import` the real
   `src/firebase.js`/services/store modules unmodified. The latter is more
   faithful (literally the app's code) but heavier to wire up standalone;
   the former is simpler but means keeping two copies of the transform logic
   in sync by hand. I'd default to duplicating (simpler, and this is a
   throwaway verification tool) unless you want strict code reuse.
